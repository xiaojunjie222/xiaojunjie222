# 机器人动作频率适配与姿态转换优化

模型一次预测一段未来动作，机器人客户端则按固定周期逐点发布目标。预测动作点比较稀疏时，需要插值补齐中间控制点；姿态插值采用四元数与 SLERP，再直接保留四元数，避免稠密轨迹上的格式往返。支持 raw 协议的执行路径进一步只传原始关键帧，由 C++ 完成插值与定时下发。

这条工程链路包含三类收益：插值适配控制节拍，四元数与 SLERP 提供合理的旋转过渡，删除重复转换与传递紧凑关键帧则减少控制端处理开销。

## 模型输出与控制下发的时间节奏

首先区分三个概念：

| 时间尺度 | 含义 | 影响因素 |
| --- | --- | --- |
| 模型请求频率 | 多久采集新观测并请求一次整块预测 | 推理延迟、执行窗口、队列余量 |
| 动作关键帧频率 | 一块预测内部，相邻动作点代表的时间间隔 | 动作时间约定与运行配置 |
| 客户端下发频率 | 多久向控制器发布一个目标 | 控制周期与执行线程调度 |

以控制周期 5 ms、插值倍率 10 的配置为例，关键帧间隔按 50 ms 解释，插值后的目标每 5 ms 发布一次，即把 20 Hz 的动作时间网格补成 200 Hz 的下发时间网格。这里的 20 Hz 不代表模型每秒推理 20 次，也不能据此判断训练数据的采样频率；200 Hz 指客户端发布频率，不是电机内部伺服频率。

例如，21 个关键帧覆盖约 1 秒，插值后得到 201 个控制点。模型负责预测目标走向，插值补充相邻目标之间的过渡，dispatcher 按固定周期消费控制点。模型不需要每 5 ms 都重新运行一次。

增加插值倍率时必须同时看动作时长。如果控制周期不变，补点更多也会让动作执行更久。每秒请求数下降，可能伴随机器人变慢；是否减少同一任务所需的模型请求，还应比较任务完成时间与成功率。

## 为什么姿态插值使用四元数

位置与夹爪等标量可以分别线性插值；三维姿态需要考虑整体旋转，直接对欧拉角的三个数字插值，不一定得到合适的旋转路径。

### 避免直接插值角度时绕远

绕同一根轴从 179° 转到 −179°，两种朝向实际只差约 2°。未经角度展开处理就直接插值这两个数值，中间会经过 0°，反而走出接近一整圈的路径。正确的四元数 SLERP 可以选择较短的旋转过渡。这个例子针对直接数值插值，并不意味着所有欧拉角控制方法都会绕远。[SciPy SLERP 说明](https://docs.scipy.org/doc/scipy/reference/generated/scipy.spatial.transform.Slerp.html)

### 避免欧拉角表示的奇异性

欧拉角在某些姿态会出现万向节锁，部分角度不能再唯一确定。使用单位四元数进行中间计算，可以避免这种欧拉角表示奇异性；它不能消除机械臂机构自身的运动学奇异位形。[SciPy 欧拉角说明](https://docs.scipy.org/doc/scipy/reference/generated/scipy.spatial.transform.Rotation.as_euler.html)

### 让一小段旋转按均匀节奏过渡

SLERP 在两个关键姿态之间沿较短路径、以该段内恒定角速度插值，适合生成均匀时间间隔上的旋转目标。四元数也需要正确处理：整体变号仍表示相同旋转，插值时要处理符号与归一化，不能简单把四个分量分别平均。[SciPy SLERP 说明](https://docs.scipy.org/doc/scipy/reference/generated/scipy.spatial.transform.Slerp.html)

这改善的是相邻姿态之间的过渡。多个关键帧或动作块交界处，旋转方向与角速度仍可能变化；真机平滑性还取决于位置轨迹、速度与加速度约束、逆运动学、下发抖动和跟踪误差。

## 插值为何引出了重复转换

上游动作使用欧拉角，SLERP 在四元数形式下插值，下游执行路径也接收四元数。旧通用插值函数为了保持原来的返回布局，在插值后又转回欧拉角，下发前再转成四元数：

```text
旧流程
Euler → quaternion → SLERP → Euler → quaternion → 控制器

保留四元数的流程
Euler → quaternion → SLERP → quaternion → 控制器
```

多余往返发生在插值后的稠密轨迹上。沿用每只手臂 21 个关键帧、201 个控制点的例子：

| 姿态处理环节 | 旧流程 | 保留四元数后 |
| --- | --- | --- |
| 原始关键帧转四元数 | 处理 21 个姿态点 | 处理 21 个姿态点 |
| SLERP 生成控制点 | 201 个 | 201 个 |
| 插值结果转回欧拉角 | 处理 201 个姿态点 | 省去 |
| 下发前再转四元数 | 再处理 201 个姿态点 | 省去 |

表中统计姿态点的处理量，实现可以批量转换，不能把 201 个点理解为 201 次 Python 函数调用。直接返回四元数数组还可以减少中间数组和嵌套列表构造。

旧链路已经使用 SLERP，所以删除转换往返主要节省 CPU 处理与临时对象，不能单凭这一改动认定姿态更平滑、精度提高或模型请求次数减少。四元数有四个分量，欧拉角有三个；保留四元数也不是通过减少字段来压缩网络数据。

## Python 与 C++ 的两种执行路径

### Python 完成插值并保留四元数

Python 接收原始 Euler 关键帧，转换为四元数并做 SLERP，直接输出下游需要的四元数控制点。实现入口为 `interpolate_end_pose_to_quat_trajectory`，EX001 的末端控制和 Desktop RTC 的 Python fallback 调用这一 helper。普通 Desktop 路径也保留插值后的四元数。关节控制不使用这套姿态转换。

### 只传原始关键帧并由 C++ 插值

Desktop RTC 在 dispatcher 已启用、末端位姿控制、raw 协议可用且非 positioning 时，使用另一条路径：

```text
原始 Euler 关键帧
  → Python 校验并保留原始数组
  → 通过 IPC 或 DDS 传关键帧与执行元数据
  → C++ 转四元数并生成稠密控制点
  → 按固定周期下发
```

Python 不再构造数百个逐步动作字典；`_RawDispatchSteps` 只保存逻辑长度，供裁剪和执行上限记账。`publish_raw_model_chunk_safe` 发布关键帧，C++ 的 `build_raw_steps` 解码后预留空间，再生成稠密轨迹。两条路径的插值位置不同，不会先在 Python 完整插值后再到 C++ 重复插值。

这减少 Python 对象、进程间 pickle 工作和 Python 到 C++ 的 DDS 负担。C++ 仍要插值并分配稠密轨迹，因此不属于零拷贝；也没有直接缩小模型服务返回的原始动作块。原始关键帧行数的下降，不能直接当成实测字节量或延迟下降比例。

## 各项优化解决什么问题

| 机制 | 解决的问题 | 收益与边界 |
| --- | --- | --- |
| 插值补点 | 稀疏预测与高频控制的时间网格不同 | 补齐中间目标，不增加新观测 |
| 四元数与 SLERP | 直接插值角度不一定得到合理旋转 | 改善单段姿态过渡，不保证全轨迹速度连续 |
| 保留四元数 | 稠密轨迹上存在格式往返 | 减少 CPU 处理，不改变模型预测与控制频率 |
| raw 关键帧协议 | Python 展开后需要处理和传递大量控制点 | 减少对象与传输负担，不是零拷贝 |
| C++ 定时下发 | 高频下发受 Python 调度与 GIL 竞争影响 | 降低执行线程干扰，不等于硬实时保证 |
| 异步与 RTC | 执行当前动作时，下一次预测尚未返回 | 重叠等待并衔接动作块，不等于单次模型前向更快 |

## 如何验证实际效果

转换优化应单独测量姿态转换耗时、控制准备时间、临时对象与 CPU 使用情况；raw 路径应比较 IPC 和 DDS 字节量、序列化耗时，以及结果返回到首条动作下发的延迟。控制质量则需要看周期抖动、队列断供、动作块接缝、实际跟踪误差和任务成功率。

这些机制解释了减少重复工作的来源；没有独立计时和真机闭环数据时，不给出加速百分比，也不把单段插值性质当成整条机器人轨迹的平滑性保证。
